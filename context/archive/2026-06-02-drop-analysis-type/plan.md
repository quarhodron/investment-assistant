# Drop Analysis Type Implementation Plan

## Overview

Remove the `analysis_type` column from the `analyses` table and delete all its scaffolding across the API, validation layer, and UI. After this plan completes, `company_id IS NULL` (unbound) vs `company_id IS NOT NULL` (watched-company-linked) is the sole discriminator — the legacy `'other'`/`'company'` enum is gone everywhere.

## Current State Analysis

The `analysis_type text NOT NULL CHECK (analysis_type IN ('other', 'company'))` column was introduced in migration `20260529120000_data_schema_and_rls.sql`. The 2026-06-01 reshape (commit `d3d5148`) decided `company_id` alone is the discriminator going forward, making `analysis_type` redundant. The column still lives in:

- DB schema: column + inline CHECK + cross-column constraint `analyses_type_company_check` + index `analyses_user_type_created_idx`
- `src/db/database.types.ts`: `analysis_type` field in Row, Insert, and Update shapes
- `src/lib/validation.ts`: field in the return type and validation logic
- `src/pages/api/ai/run.ts`: reads `input.analysis_type`, writes into the `AnalysisInsert` row
- `src/components/NewAnalysisForm.tsx`: hardcodes `analysis_type: "other"` in the payload
- `src/components/ContinueAnalysisForm.tsx`: `ParentAnalysis` interface prop, `ANALYSIS_TYPES` constant, `analysisType` state, dropdown UI, payload field
- `src/pages/analyses/index.astro`: in select projection, renders as purple badge
- `src/pages/analyses/[id]/index.astro`: renders as purple badge in the detail header
- `src/pages/analyses/[id]/continue.astro`: in the parent analysis select projection

## Desired End State

The `analyses` table has no `analysis_type` column, no `analyses_type_company_check` constraint, and no `analyses_user_type_created_idx` index. All application code compiles and passes lint with no reference to `analysis_type`. The UI shows no type badge. Running `npx supabase start` and regenerating types yields a `database.types.ts` that contains no `analysis_type` fields.

### Key Discoveries

- The cross-column constraint `analyses_type_company_check` depends on `analysis_type`, so it must be dropped before the column itself (`ALTER TABLE analyses DROP CONSTRAINT analyses_type_company_check`).
- The inline `CHECK (analysis_type IN ('other', 'company'))` is an unnamed inline constraint — it is dropped implicitly when the column is dropped.
- `analyses_user_type_created_idx` is a standalone index — must be explicitly dropped.
- `src/db/database.types.ts` is regenerated by `npx supabase gen types typescript --local` (requires Docker + `npx supabase start`).
- `analyses/[id]/index.astro` uses `.select("*")` which will naturally exclude the dropped column after regeneration; the `analysis.analysis_type` reference on line 76 must still be deleted.
- `ContinueAnalysisForm.tsx` passes `analysis_type` via the `ParentAnalysis` interface and through the API payload — both must be removed together so TypeScript is satisfied.

## What We're NOT Doing

- Adding a replacement `company_id`-based badge or indicator — that is S-06/S-07 scope.
- Showing company context (name, ticker) anywhere in the continue flow — that is S-06 scope.
- Migrating or backfilling existing rows — no data transformation needed; the column is informational only.
- Writing any new filtering, querying, or display logic around `company_id` — that is S-03/S-06/S-07 scope.

## Implementation Approach

Two sequential phases: schema first, application code second. Applying the DB migration before touching application code means the local Supabase schema matches the freshly generated types when Phase 2 begins, so TypeScript errors are the guide for finding every remaining reference.

## Critical Implementation Details

**Migration ordering**: the named constraint `analyses_type_company_check` must be dropped before the column. Postgres will reject dropping the column while a named constraint referencing it exists. The inline CHECK on the column itself does not require a separate DROP — it is dropped with the column.

**Types-file regeneration prerequisite**: Phase 2 cannot start until `database.types.ts` is regenerated post-migration. The implementer must run `npx supabase start` (Docker required), apply the migration, then run `npx supabase gen types typescript --local > src/db/database.types.ts`. Only after regeneration will the TypeScript compiler flag the stale callsites.

## Phase 1: Schema Migration & Type Regeneration

### Overview

Write and apply the SQL migration that drops the constraint, index, and column from `analyses`. Then regenerate `src/db/database.types.ts` to reflect the new schema. Phase 1 is complete when the local DB and generated types are in sync and contain no trace of `analysis_type`.

### Changes Required

#### 1. New migration file

**File**: `supabase/migrations/20260602000000_drop_analysis_type.sql`

**Intent**: Create a forward-only migration that removes the `analysis_type` column and its associated named constraint and index from the `analyses` table.

**Contract**: The migration must execute in this order:
1. `ALTER TABLE analyses DROP CONSTRAINT analyses_type_company_check;`
2. `DROP INDEX analyses_user_type_created_idx;`
3. `ALTER TABLE analyses DROP COLUMN analysis_type;`

No rollback section needed — this is an additive cleanup, and the column carries no data the app uses going forward.

#### 2. Regenerate database types

**File**: `src/db/database.types.ts`

**Intent**: Re-run the Supabase type generator after applying the migration so the TypeScript types for `analyses` Row, Insert, and Update no longer include `analysis_type`.

**Contract**: Run `npx supabase gen types typescript --local > src/db/database.types.ts`. The resulting file's `analyses.Row`, `analyses.Insert`, and `analyses.Update` shapes must not contain `analysis_type`.

### Success Criteria

#### Automated Verification

- Migration applies cleanly: `npx supabase db reset` (or `npx supabase migration up`) completes without error
- `database.types.ts` no longer contains the string `analysis_type`: `grep -c 'analysis_type' src/db/database.types.ts` outputs `0`
- Type check passes (stale callsites will now surface as errors): `npx astro check`

#### Manual Verification

- Local Supabase dashboard (or `psql`) confirms `analyses` table has no `analysis_type` column and no `analyses_type_company_check` constraint

## Phase 2: Application Code Cleanup

### Overview

Remove every reference to `analysis_type` from validation, API handler, React components, and Astro pages. The TypeScript errors produced after Phase 1's type regeneration are the canonical guide — fix all of them, then verify no stray references remain.

### Changes Required

#### 1. Validation layer

**File**: `src/lib/validation.ts`

**Intent**: Remove `analysis_type` from the `validateRunInput` return type and from the validation body so the API no longer accepts or validates this field.

**Contract**: Delete `analysis_type: string` from the return type on line 36, delete the `validAnalysisTypes` check block (lines 70–73), and delete `analysis_type: b.analysis_type as string` from the returned `value` object (line 86).

#### 2. API route

**File**: `src/pages/api/ai/run.ts`

**Intent**: Remove `analysis_type` from the `AnalysisInsert` row construction so the insert no longer sets this column.

**Contract**: Delete `analysis_type: input.analysis_type,` from the `row` object on line 148.

#### 3. New analysis form

**File**: `src/components/NewAnalysisForm.tsx`

**Intent**: Remove the hardcoded `analysis_type: "other"` from the API payload.

**Contract**: Delete `analysis_type: "other",` from the `payload` object on line 131.

#### 4. Continue analysis form

**File**: `src/components/ContinueAnalysisForm.tsx`

**Intent**: Remove all `analysis_type` references — the `ParentAnalysis` interface prop, the `ANALYSIS_TYPES` constant, the `analysisType` state, the dropdown UI block, and the payload field.

**Contract**: Remove:
- `analysis_type: string;` from the `ParentAnalysis` interface (line 9)
- The `ANALYSIS_TYPES` constant (lines 105–108)
- `const [analysisType, setAnalysisType] = useState(parentAnalysis.analysis_type);` (line 120)
- `analysis_type: analysisType,` from the payload object (line 157)
- The entire "Analysis type" `<div>` block in the JSX (lines 321–341)

#### 5. Analyses list page

**File**: `src/pages/analyses/index.astro`

**Intent**: Remove `analysis_type` from the Supabase select projection and delete the badge element that renders it.

**Contract**: Remove `analysis_type` from the select string on line 9 and from the `.select(...)` call on line 14. Remove the `<span>` badge element that renders `{analysis.analysis_type}` on lines 52–54. Update the `Pick<Analysis, ...>` type annotation on line 9 to exclude `analysis_type`.

#### 6. Analysis detail page

**File**: `src/pages/analyses/[id]/index.astro`

**Intent**: Remove the `analysis_type` badge from the detail view header.

**Contract**: Delete the `<span>` element on lines 75–77 that renders `{analysis.analysis_type}`. The page uses `.select("*")` — no projection change needed; the dropped column simply won't appear in the returned row.

#### 7. Continue analysis page

**File**: `src/pages/analyses/[id]/continue.astro`

**Intent**: Remove `analysis_type` from the parent analysis select projection passed to `ContinueAnalysisForm`.

**Contract**: Remove `analysis_type` from the `.select(...)` string on line 20. The `parentAnalysis` object will no longer carry this field; since `ContinueAnalysisForm`'s `ParentAnalysis` interface was updated in step 4, TypeScript will confirm the types align.
